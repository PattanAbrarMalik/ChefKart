# Understand the complete project

The source is formatted for reading. Comments above modules, functions and important blocks explain their purpose. This guide explains the remaining connections so you can follow the whole project without guessing.

## A useful starting point

A **frontend** displays pages and collects input. A **backend** receives HTTP requests, checks them, and reads/writes data. A **REST API** is the agreed set of URLs and HTTP methods between them. A **database** keeps records after the browser or server closes.

For this project:

- React renders the frontend.
- React Router selects a page from the URL.
- Express runs the backend and routes HTTP requests.
- Middleware runs before/after controllers to handle common concerns.
- Controllers implement each operation.
- Validation checks allowed fields and values.
- The store saves records to local JSON or MongoDB.

## A booking, from button to saved record

1. Open `/chef/ID`. `ChefDetail.jsx` calls `useApi('/chefs/ID')` to fetch the profile.
2. `useApi.js` calls the shared `api()` function. It requests `GET /api/chefs/ID`.
3. In development, Vite forwards `/api` to Express on port 8000. In a built app, Express receives it directly.
4. `routes/api.js` matches the URL to `chefController.detail`.
5. The controller loads the chef through `store.get()` and removes private contact fields with `publicChef()`.
6. React renders the name, location, cuisines and booking form.
7. Submit the form. `BookingForm.jsx` reads the inputs, converts the date to an ISO timestamp, and calls its `onSave` prop.
8. `ChefDetail.jsx` sends `POST /api/bookings` with the selected chef ID and form values.
9. `api.js` adds `Authorization: Bearer <token>` from session storage.
10. `requireAuth` verifies the JWT and loads the user from the database. It assigns that user to `req.user`.
11. `bookingController.create` validates the date, service, guests and address, checks the chef, calculates the estimate, and chooses the booking owner/status itself.
12. `store.create` rejects an identical active slot, assigns ID/timestamps, and persists the booking.
13. The server returns status 201 with `{ data: booking }`.
14. React navigates to My bookings, which loads the saved records using `GET /api/bookings`.
15. If anything fails, an error response is displayed. The interface does not pretend a failed request succeeded.

## Backend: startup and application

### `backend/config/env.js`

Loads environment settings before other modules use them. Uses the file's location to resolve the backend folder, so execution from a different directory does not break paths. Creates the data directory. In development it generates a random signing key once and reuses it after restarts. In production a configured secret is required. The exported `config` object provides port, host, secret, MongoDB URI, seed flag and allowed browser origins.

### `backend/server.js`

Starts the application in a deliberate order: connect the data store, insert starter records if enabled, then listen for HTTP requests. A failed database connection stops startup visibly. SIGINT/SIGTERM stop accepting new requests and close the database connection.

### `backend/app.js`

Creates and exports the Express application separately from starting it. Tests can therefore start the same app on their own free port. Middleware adds response headers, checks allowed origins, parses JSON with a size limit, validates the body shape, and disables caching of API responses. Routes are mounted under `/api`. Unknown API routes return JSON 404 responses. If a frontend build exists, static files and client-side page routes are also served. The final error middleware formats errors.

### `backend/routes/api.js`

This is the backend's URL map. Each route declares the method, path, optional permission middleware, and controller. Static `/chefs/manage` and `/chefs/mine` appear before `/chefs/:id` so they are not mistaken for a chef ID. Read this file alongside API.md.

## Backend: middleware explained

| File/function | Role and why it exists |
|---|---|
| `middleware/auth.js` → `signToken(user)` | Creates a signed JWT with the user's ID as subject and an eight-hour lifetime. A signature prevents clients from silently changing the identity. |
| `requireAuth(req,res,next)` | Reads the Bearer token, verifies its signature/expiry, loads the current user and calls `next()`. Rejects missing, invalid or expired sessions with 401. |
| `requireAdmin(req,res,next)` | Checks the authenticated user's database role. Rejects a customer with 403. Frontend hidden buttons alone would not secure an API. |
| `requireOwner(user,ownerId)` | Allows only the record owner or an admin. Used for profile/booking edits, reads and deletion. |
| `publicUser(user)` | Selects safe account fields. Password hashes never appear in API responses. |
| `middleware/errors.js` → `asyncHandler(handler)` | Express 4 needs rejected async promises forwarded to `next(error)`. This wrapper avoids repeating try/catch in every controller. |
| `notFound` | Returns a clear JSON 404 instead of an HTML error page. |
| `errorHandler(error,req,res,next)` | Maps expected errors and duplicate-key conflicts to consistent JSON; hides unexpected internal details from clients. It must have four arguments and run last. |
| `middleware/rateLimit.js` → `rateLimit(max,windowMs)` | Counts requests per IP for login/signup and public enquiries. Returns 429 plus `Retry-After` when the limit is reached. Cleans up expired entries. This limiter is intentionally single-process. |

`req` is the incoming request. `res` is how the server replies. `next()` means “continue to the next middleware/controller.” `next(error)` skips ordinary handlers and reaches the error handler. Middleware ordering matters: authentication must run before authorization.

## Backend: validation and models

### `backend/models/validation.js`

Controllers use these plain JavaScript validation functions in both storage modes. MongoDB mode now also uses the explicit Mongoose schemas described below. This gives request-level feedback plus model validation at the persistence boundary.

| Function | Checks |
|---|---|
| `fail` | Throws an error with an HTTP status. |
| `text` | Requires a string, trims it, checks min/max length. |
| `optionalText` | Allows missing/empty strings while keeping length limits. |
| `email` | Checks a practical email pattern and normalizes to lowercase. |
| `number` | Checks a finite numeric value and its allowed range. |
| `choice` | Accepts only a listed enum value. |
| `imagePath` | Allows an HTTPS image URL or local `/assets/` path. |
| `futureDate` | Requires a valid future date and normalizes it to ISO format. |
| `stringList` | Validates bounded arrays of strings. |
| `chefValues` | Builds the allowed editable fields of a chef profile. |
| `contentValues` | Builds title/content/category/image for a content record. |
| `leadValues` | Builds contact details/message/type for an enquiry. |

Controllers do not save `req.body` directly. They select approved fields. That prevents clients from setting server-owned IDs, passwords, owners, verification flags or booking prices through mass assignment. React validation makes forms convenient; server validation remains necessary because callers can bypass the browser.

## Backend: controllers

| File | Functions and behaviour |
|---|---|
| `authController.js` | `signup`: validate, reject duplicate email, hash password using bcrypt, store a customer, return token. `login`: find email, compare password hash, return token. `me`: return current safe user. |
| `chefController.js` | `publicChef`: remove private fields. `findChef`: load or 404. `list`: search/filter/sort public profiles. `detail`: one public profile. `mine`: current user's private editable profile. `create`: one profile per account. `update`: owner/admin editing; verification is admin-only. `remove`: owner/admin deletion, blocked while booking references exist. `manage`: full private list for administrators only. |
| `bookingController.js` | `ownedBooking`: load and authorize. `bookingValues`: validate editable fields. `withChef`: add a chef name/city to the response. `list`/`detail`: return only authorized records. `create`: derive owner/status/estimate on server. `update`: reschedule, change notes/address/service, cancel; only admin can complete. Closed bookings cannot reopen. `remove`: delete only closed bookings. |
| `contentController.js` | `collection`: validate the type against the allowlist. `list`/`detail`: public reads. `create`/`update`/`remove`: admin CRUD for all content types. Merges edits with existing data so omitted image fields are preserved. |
| `leadController.js` | `create`: save an enquiry and return only a receipt. `list`/`detail`: private admin reads. `update`: mark new/resolved. `remove`: delete one enquiry. Contact, investor and career requests use one collection with a type field. |

## Backend: persistence

### `backend/services/store.js`

All controllers depend on five methods: `list`, `get`, `create`, `update`, `remove`.

- `connectStore()` selects MongoDB if a URI is configured, waits for all Mongoose models and unique indexes, otherwise reads the local JSON database. It does not erase unreadable data.
- `list(collection)` runs the selected model's `find().lean()` in MongoDB mode; the simple controllers filter small lists in JavaScript.
- `get(collection,id)` uses `findById().lean()` in MongoDB mode and returns one record or `null`.
- `create(collection,values)` assigns a random 24-character ID and timestamps. It enforces unique emails, one chef profile per owner, and a unique active chef/start-time booking.
- `update(collection,id,values)` preserves IDs/creation time and updates `updatedAt`. Local mode checks slot uniqueness before writing. MongoDB uses `findByIdAndUpdate()` with `new: true`, `runValidators: true`, and its unique index.
- `remove(collection,id)` uses `findByIdAndDelete()` in MongoDB mode and removes one matching record. There is no delete-all API.
- `persist()` writes JSON to a temporary file, then renames it. This reduces the risk of leaving half-written JSON after interruption.
- `closeStore()` disconnects MongoDB cleanly.

Local mode must have only one writing process. Stop the server before running `npm run admin`. MongoDB mode uses actual Mongoose models. The store keeps its existing string IDs and ISO timestamp strings for compatibility with the supplied v2 project. The standalone Student lab demonstrates native ObjectId IDs. Existing database migration is not automatic.

### Collections

| Collection | Important fields |
|---|---|
| `users` | `_id`, name, normalized email, bcrypt password hash, role, timestamps |
| `chefs` | ownerId, public profile details/cuisines/price, private address/email/phone, verification, sample marker, timestamps |
| `bookings` | user ID, chef ID, bookingDate, service, address, guests, notes, status, estimatedPrice, timestamps |
| `leads` | type, name, email, optional phone/area, city, message, new/resolved status, timestamps |
| `content_<type>` | title, content, category, optional image, timestamps |
| `metadata` | Seed-completion marker so deleted sample content stays deleted |

### `backend/services/seed.js`

`seedData()` inserts sample chefs and starter content into empty collections once. There are no seeded login credentials. Samples are labelled and verification remains false. A completion marker prevents reseeding after an intentional deletion.

### `backend/scripts/create-admin.js`

Interactive local provisioning command. Uses the same validators, hashing and storage as signup, but explicitly assigns admin role. It refuses existing email addresses rather than secretly changing an existing user. The script is not exposed as a public API.

### `backend/tests/api.test.js`

Starts the real Express app with a temporary data directory and a random HTTP port. Exercises all REST resources, permissions, invalid input and disk persistence. Closes the server and deletes only its own temporary directory afterward.

## Frontend: entry and shared logic

| File | What each part does |
|---|---|
| `main.jsx` | Loads global CSS and renders React inside `root`. Wraps the app in error handling, browser routing and shared authentication. StrictMode helps reveal development lifecycle issues. |
| `App.jsx` | Maps browser paths to pages. `Protected` wraps pages requiring login/admin access. Both `/register` and `/register-chef` resolve to cook registration. Unknown URLs show a 404 page. |
| `services/api.js` | `api(path,options)` performs fetch, adds the token, serializes JSON, handles 204, parses responses and throws readable errors. Session expiry dispatches an event. `money` formats rupees. `serviceLabels` maps stored service keys to user-friendly labels. |
| `hooks/useApi.js` | Reusable GET hook. Maintains data/loading/error, aborts old requests on navigation and exposes `reload()`. Failed requests show errors; they do not substitute fake records. |
| `context/AuthContext.jsx` | Loads `/auth/me` on startup when a token exists. `authenticate` signs in/up and updates shared user state. `logout` removes the tab's token. Session-expiry events clear the user. `useAuth` lets any component read this shared state. |
| `components/ErrorBoundary.jsx` | Catches rendering exceptions, logs them for debugging and shows a reload action instead of a blank page. |

`useState` keeps changing local UI values. `useEffect` runs work when dependencies change and can clean it up. A **prop** is a value/function supplied to a component. A hook is a reusable function that uses React state/lifecycle. JSX is HTML-like syntax that compiles to React element creation.

## CSS: understand the styling

`frontend/src/styles.css` is intentionally one plain CSS file with numbered, commented sections:

1. **Design tokens:** brand colours, spacing-related values and fonts.
2. **Base styles:** predictable box sizing, typography, containers, buttons and focus states.
3. **Navigation:** desktop links and the mobile-only menu button.
4. **Home:** hero, search strip, service/chef grids, steps and join banner.
5. **Forms and states:** common inputs, errors, success, empty lists and loading.
6. **Pages:** profile, bookings, authentication, contact and article layout.
7. **Admin:** wrapping rows instead of wide, overflowing tables.
8. **Footer and media queries:** grids collapse at 1100/850/600 pixels; reduced-motion support.

The global `box-sizing: border-box` includes padding inside widths. `minmax(0,1fr)` allows grid children to shrink instead of stretching the whole page. Containers have a maximum width and small-screen side margins. The header uses `position: sticky`, which reserves its normal layout space. Images are constrained by `max-width: 100%`. These choices directly address the screenshots' overflow, overlapping header and oversized elements.

## Extending it without making it confusing

To add a field: update validation, its form, any public/private projection, API documentation and a meaningful test. To add a new operation: add a controller function, route, API call and UI action. To change presentation: edit the shared component or CSS section, not several duplicated screens. To add a real payment/email service: place its SDK behind a new backend service; keep secrets out of frontend code.
